Case 01

인사 자원 시스템 — 멀티 테넌시 아키텍처 설계

2024.07 ~ 2024.12 · 주식회사 디케이테크인

Problem

다수의 조직(테넌트)이 하나의 인사 자원 관리 시스템을 공유해야 하는 요구사항이 있었습니다. 각 조직마다 별도 시스템을 구축하면 유지보수 비용이 기하급수적으로 증가하고, 조직 추가 시마다 인프라를 별도로 구성해야 하는 구조적 한계가 있었습니다.

  • 조직마다 독립적인 데이터 격리가 필요하지만, 인프라 비용과 개발 일정을 최소화해야 함
  • 새로운 조직 추가 시 코드 변경 없이 확장 가능한 구조가 필요
  • 테넌트별 주기적 데이터 동기화(공휴일, 급여 마감일 등)를 서비스에 영향 없이 처리해야 함
Analyze

멀티 테넌시 구현 방식은 크게 세 가지가 있었습니다. DB 인스턴스 분리는 격리성이 높지만 테넌트 수만큼 DB를 운영해야 해서 비용과 관리 부담이 컸고, 스키마 분리는 JPA 설정 복잡도가 높아 제한된 일정 안에 안정적으로 구현하기 어렵다고 판단했습니다. 비용과 시간을 고려했을 때 컬럼 분리 방식이 가장 현실적이었습니다.

테넌트 분리 방식 비교

DB 분리
비용 ↑ 관리 부담 ↑ vs 스키마 분리
JPA 복잡도 ↑ 일정 초과 vs 컬럼 분리 ✓
비용 ↓ 확장성 ↑
Action

1. Shared Database + Shared Schema 채택

단일 DB에서 TENANT_ID / COMPANY_ID 컬럼으로 데이터를 격리하는 방식을 선택했습니다. 애플리케이션 레벨의 쿼리 필터링(WHERE COMPANY_ID)으로 데이터를 격리하고, 단일 HikariCP 커넥션 풀로 운영하여 리소스 관리를 단순화했습니다. WHERE 조건 누락 시 데이터 노출 위험이 있어 코드 리뷰 시 쿼리 필터링 누락 여부를 중점 검토하는 프로세스를 마련했습니다.

2. 인증 및 세션 — 테넌트별 격리

Keycloak OIDC 인증 후 OidcUserDto에서 companyId를 추출하여 UserDetail에 주입하는 구조로, 인증 시점부터 테넌트 식별이 자연스럽게 이루어지도록 했습니다. 세션은 Redis에 테넌트별 네임스페이스를 적용하여 테넌트 간 세션 충돌을 방지했습니다.

인증 → 테넌트 식별 흐름

Keycloak OIDC → OidcUserDto → UserDetail (companyId) → 쿼리 필터링

3. 배치 처리 분리

테넌트별 주기적 데이터 동기화를 별도 schedule-module로 분리하여 Spring Batch 기반으로 처리했습니다. 서비스 모듈에 영향을 주지 않으면서 테넌트별 데이터를 순차 처리하는 구조입니다.

Result
  • 단일 DB 구조로 인프라 비용을 최소화하면서 다수 조직의 데이터 격리 확보
  • Keycloak 인증 + Redis 세션 네임스페이스로 인증 및 세션 레벨의 테넌트 격리 보장
  • 배치 모듈 분리로 주기적 동기화 작업이 서비스 안정성에 영향을 주지 않는 구조 확보
  • 신규 테넌트 추가 시 설정 기반 테넌트 식별로 빠른 온보딩 가능

Case 02

카카오 휴양지 예약 시스템 — Redis 분산 락 기반 동시성 제어

2024.01 ~ 2024.05 · 주식회사 디케이테크인

Problem

카카오 임직원 대상 휴양지 예약 시스템에서, 인기 휴양지 예약 오픈 시 동일 사용자의 중복 예약이 발생하는 실제 장애가 있었습니다.

  • 동일 사용자가 짧은 시간 내 중복 요청을 보낼 경우, 애플리케이션 레벨의 중복 체크만으로는 동시 요청을 차단하지 못함
  • 단순 synchronized 처리는 멀티 서버 환경에서 서버 간 상태를 공유하지 않아 동작하지 않음

장애 상황

사용자 A 요청 1 → 서버 1 → 중복 예약 발생
사용자 A 요청 2 → 서버 2 → 중복 예약 발생
Analyze

멀티 서버 환경에서 동시성 제어 방안을 조사한 결과, Redis 기반 분산 락이 적합하다고 판단했습니다. 이미 세션 관리에 Redis를 사용하고 있어 추가 인프라 없이 적용 가능했고, Redisson 라이브러리가 분산 락에 대한 안정적인 구현을 제공하고 있었습니다.

Action

1. Redisson 분산 락 도입

락 키를 userId:startDate:endDate 패턴으로 설계하여, 동일 사용자가 같은 날짜에 중복 예약을 시도하는 것을 서버와 관계없이 차단하도록 했습니다. tryLock(10, TimeUnit.MILLISECONDS)으로 10ms 내에 락을 획득하지 못하면 즉시 "같은 날짜에 두번 이상 신청하실 수 없습니다"로 응답하여 빠른 피드백을 제공합니다.

2. 안전한 락 해제

락 획득 후에는 패널티 체크, 연간 신청일수 제한, 잔여 객실 확인 등 비즈니스 검증을 순차 수행하고, finally 블록에서 isHeldByCurrentThread() 확인 후 안전하게 락을 해제하여 장애 상황에서의 데드락을 방지했습니다.

해결 후 흐름

예약 요청 → Redisson 락 획득 → 비즈니스 검증 + 예약 → finally 락 해제
Result
  • 멀티 서버 환경에서 동일 사용자의 중복 예약 장애 재발 방지
  • 10ms 타임아웃으로 중복 요청 시 빠른 사용자 피드백 제공
  • finally 블록 기반 안전한 락 해제로 데드락 방지
Java Spring Boot JPA Redis

Case 03

다음 검색 미들웨어 — Jenkins + Ansible 기반 CI/CD 파이프라인 구축

2026.01 ~ 현재 · 주식회사 디케이테크인

Problem

다음 포털 검색 미들웨어 서비스는 다수의 운영 서버에 배포되는 구조였지만, 기존에는 수동으로 빌드하고 각 서버에 직접 접속하여 배포하는 방식이었습니다.

  • 다수 서버에 대한 수동 배포로 인해 배포 시간이 길고 휴먼 에러 발생 가능성이 높음
  • 환경별(dev/stage/prod) 빌드·배포 프로세스가 통일되지 않아 환경 간 불일치 발생
  • 배포 실패 시 롤백 절차가 수동이라 장애 복구 시간이 길어지는 구조
  • 배포 중 서비스 중단 없이 트래픽을 처리해야 하는 무중단 배포 요구사항
Analyze

빌드 자동화, 무중단 배포, 배포 실패 시 자동 복구를 모두 해결해야 하는 상황이었습니다. 빌드·테스트 자동화는 Jenkins 파이프라인으로, 다수 서버에 대한 배포 자동화는 Ansible Playbook으로 역할을 분리하는 것이 가장 효과적이라고 판단했습니다. 특히 운영 환경은 서버 수가 많아 롤링 배포 전략이 필수적이었고, 배포 실패 시 자동 롤백을 위한 릴리스 관리 구조가 필요했습니다.

Action

1. Jenkins 파이프라인 — 환경별 분기 전략

Jenkinsfile 기반 선언적 파이프라인을 구성하여 빌드부터 배포까지 자동화했습니다. 환경 파라미터(dev/stage/prod)에 따라 브랜치를 자동 선택하고, Maven 빌드 및 테스트를 거쳐 배포 아티팩트를 생성합니다. 운영 환경 배포 시에는 수동 승인(Approval) 단계를 추가하여 의도하지 않은 배포를 방지했습니다.

Jenkins 파이프라인 흐름

Git Checkout → Maven Build & Test → Approval (prod) → Ansible Deploy

2. Ansible 롤링 배포

서버 한 대씩 순차적으로 배포하는 롤링 배포 전략을 적용했습니다. 배포 대상 서버를 로드밸런서에서 제거(Health Check DOWN)한 뒤 트래픽이 완전히 빠질 때까지 대기하고, 새 버전을 배포한 후 다시 등록(Health Check UP)하는 방식으로 서비스 중단 없이 배포를 수행합니다.

롤링 배포 흐름 (서버 1대 기준)

Health Check DOWN → 트래픽 드레인 → 아티팩트 배포 → 서비스 재시작 → Smoke Test → Health Check UP

3. 자동 롤백 및 안정성 확보

릴리스 디렉토리를 타임스탬프 기반으로 관리하고 심볼릭 링크로 현재 버전을 가리키는 구조를 적용하여, 배포 실패 시 이전 릴리스로 심볼릭 링크를 즉시 복원하는 자동 롤백을 구현했습니다. 새 버전 배포 후에는 Smoke Test로 핵심 API의 정상 응답을 검증하고, Warmup 과정을 거쳐 커넥션 풀과 캐시가 초기화된 상태에서 트래픽을 받도록 했습니다.

배포 실패 시 자동 롤백

배포 실패 감지 → 심볼릭 링크 복원 → 이전 버전 재시작 → Health Check UP

4. 환경별 구성 관리

Ansible Inventory를 환경별(dev/stage/prod)로 분리하여 서버 목록, 서비스 포트, 배포 경로 등을 관리하고, Jinja2 템플릿을 활용하여 설정 파일과 서비스 제어 스크립트를 환경 변수 기반으로 자동 생성하여 환경 간 설정 불일치를 방지했습니다.

Result
  • 수동 배포에서 Jenkins 파이프라인 기반 자동화로 전환하여 배포 시간 단축 및 휴먼 에러 제거
  • 롤링 배포 전략으로 다수 서버에 대한 무중단 배포 달성
  • 자동 롤백 구조로 배포 실패 시 빠른 장애 복구 가능
  • Smoke Test + Warmup 과정을 통해 배포 직후 서비스 안정성 확보
  • 환경별 Inventory 및 템플릿 분리로 dev/stage/prod 간 설정 일관성 유지
